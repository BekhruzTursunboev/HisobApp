# Hisob

**Hisob** is Uzbek for *the bill* - the word you say when you want to pay.

A spend tracker for international students. Log what you spend, split bills with the
people you actually eat with, and add a budget only if you want one.

Two ways to run it:

| | |
|---|---|
| **`hisob.html`** | the whole app in one file. Open it, works offline, no server, no accounts. |
| **this project** | the same app plus a Neon database, so your entries survive a lost phone and a friend can confirm their half of a bill. |

---

## Before anything else: rotate your password

If a Neon connection string has ever been pasted into a chat, a screenshot, a commit or
a message, **it is compromised** — that string is full read, write and drop access to
your database.

Neon dashboard → **Connect to your database** → **Reset password** (top right of the
Role field). Then use the new one everywhere below.

Rules that keep this from happening again:

- The connection string lives in `.env.local`, which is gitignored. Nowhere else.
- Never in anything under `public/` — that directory is served to every visitor.
- Never in a chat window.

## Setup

```bash
npm install
```

```bash
cp .env.example .env.local
```

Open `.env.local` and paste your **new** connection string — the one with `-pooler` in
the host, since serverless functions open and drop connections constantly and the pooler
is what absorbs that.

Create the tables:

```bash
npm run db:push
```

Confirm it worked:

```bash
npm run db:check
```

That prints the round-trip time. **Run it on campus wifi.** If it is slow or fails from
Kunshan but works elsewhere, you have your answer about hosting in `us-east-2` and should
move the database to a closer region before you build anything else on it.

Build and run it locally:

```bash
npm run dev
```

That builds both copies and serves them at http://localhost:3000.

Test the API against the real database:

```bash
npm run test:api
```

## Deploying

```bash
npx vercel deploy
```

Then add `DATABASE_URL` in the Vercel dashboard under Settings → Environment Variables.
Vercel serves `public/` as static files and turns each file in `api/` into its own
serverless function — no framework, no build step.

## Installing it on a phone

Once deployed over HTTPS, open the site and add it to the Home Screen. That is not
cosmetic — **Safari deletes a normal website's stored data after 7 days without a visit,
and Home Screen web apps are exempt.** Installing is what makes the history survive.

The app shows the instructions itself: Android and desktop Chrome get a real Install
button, iOS gets a one-line explanation of the Share → Add to Home Screen path, and both
disappear for good once dismissed or installed.

What makes it installable: HTTPS, `manifest.webmanifest` with `display: standalone`,
icons at 192/512 plus a maskable 512, and a service worker with a fetch handler. All four
are required — miss one and it opens in a browser tab with an address bar instead.

## How it fits together

```
src/app.html        THE SOURCE. Edit this, never the builds.
  -> npm run build
     hisob.html           standalone build: no server, no install
     public/index.html    hosted build: full document, PWA head, service worker

api/register.js     claim an account from a device key
api/sync.js         push local changes and pull server changes in one round trip
api/split.js        create a shared bill, open it by link, confirm your share
lib/db.js           the Neon client, auth, and validation helpers
db/schema.sql       tables, constraints, indexes
public/sw.js        offline: API never cached, shell cached, navigations network-first
public/icons/       generated by `npm run icons` — the app's dial, drawn in code
scripts/serve.js    local server that mimics Vercel's routing
scripts/e2e.js      36 tests against the real database
```

**Never edit `public/index.html` or `hisob.html` by hand** — they are generated
and your changes will vanish on the next build. Two hand-maintained copies is exactly how
a CSS class collision once survived long enough to ship.

**Local first.** The app reads and writes local storage and renders from it. Sync runs
afterwards in the background. If the API is missing, unreachable, or the page is opened
as a plain file, sync switches itself off and the app carries on working — that is why
the single-file version still works with no server at all.

**Accounts without passwords.** Each device generates a 256-bit random key on first run
and keeps it locally. The server stores only its SHA-256, so a database leak hands
nobody a working credential. There is nothing to remember and nothing to phish.

**Entry ids are made on the client.** A push that times out and gets retried updates the
same row instead of creating a duplicate.

**Deletes are soft.** A device that was offline when you deleted something still finds
out about it on the next sync, instead of resurrecting the row.

**Money is `numeric(12,2)`, never a float.** `0.1 + 0.2` has to equal `0.3` exactly when
it is somebody's rent.

**Every query is parameterised.** `sql` is a tagged template, so interpolations become
bound parameters and cannot be injected.

## What is deliberately missing

- **Rate limiting.** Anyone can call `/api/register` in a loop and fill the users table.
  Fine for a class of friends, not fine at a thousand users. Add it before you post the
  link publicly.
- **Real accounts.** Lose the device and you lose the key. There is no recovery. The
  backup file in the app is the answer for now; email sign-in is the answer later.
- **A shared-bill UI.** `api/split.js` works, but the app does not call it yet. That is
  the next thing worth building, and the only reason this database exists.
